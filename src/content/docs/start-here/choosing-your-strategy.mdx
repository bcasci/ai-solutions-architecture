Over-engineering happens before a single line of code is written. Teams reach for agents when a prompt would do, build RAG when the document fits in context, or add orchestration layers that only slow things down. This page helps you make the right architectural decisions upfront.

## Pick Your Starting Point

Three products, three use cases. You can combine them in a single project.

| Product | Use when | You manage |
| --- | --- | --- |
| **Messages API** | Building product features — chatbots, content generation, extraction, RAG pipelines, any custom app | Prompt construction, conversation state, tool definitions, error handling |
| **Claude Code** | Automating development workflows — writing code, exploring codebases, running multi-step dev tasks | `.claude/` config, commands, hooks, skills |
| **Agent SDK** | Building autonomous multi-step agents that plan, use tools, and make decisions in a loop | Agent definitions, tool registrations, guardrails |

Most teams start with the **Messages API** for their product and **Claude Code** for their development workflow. Add the **Agent SDK** when you outgrow single-turn tool use in production.

## How Complex Does Your System Need to Be?

Start at the simplest level that works. Move up only when you hit a specific limitation.

### Level 1: Single Prompt

One API call, one response. This covers summarization, classification, extraction, code generation, Q&A, and even multi-step reasoning.

You can structure a workflow *inside* the prompt itself:

```
Analyze this support ticket in three steps:
1. Identify the core issue
2. Classify severity (P0-P3)
3. Draft a response

<ticket>{ticket_text}</ticket>
```

Claude follows the steps within one call. No Python orchestration, no multiple API calls. **Try this first.**

### Level 2: Scripted Workflow

Your code orchestrates multiple API calls. You control the steps — Claude handles each one.

```python
# You define the flow. Each step is a focused Claude call.
draft = generate(topic)          # Step 1: Claude generates
issues = validate(draft)         # Step 2: your code or Claude checks
final = revise(draft, issues)    # Step 3: Claude fixes
```

Four building blocks you can combine freely:

| Pattern | What it does | Use when |
| --- | --- | --- |
| **[Chain](/agents/orchestration#chaining-sequential-steps)** | Sequential steps, each feeds the next | Output of step N depends on step N-1 |
| **[Route](/agents/orchestration#routing-classify-then-specialize)** | Classify input, dispatch to a specialized handler | Different input types need different handling |
| **[Parallelize](/agents/orchestration#parallelization-independent-sub-tasks)** | Run independent subtasks concurrently, aggregate | Subtasks don't need each other's output |
| **[Evaluator-Optimizer](/agents/orchestration#evaluator-optimizer-iterative-refinement)** | Generate, evaluate, loop until quality threshold met | Output quality varies and needs iterative refinement |

These are **composable**, not a ladder. A router can dispatch to chains. A chain step can parallelize internally. Pick whichever ones apply.

### Level 3: Agent Loop

Give Claude tools and a goal. It decides what to do, observes results, and iterates. You don't predetermine the steps — Claude does at runtime.

```python
# You provide tools and a goal. Claude decides the steps.
while not done:
    response = claude(messages, tools)
    if response.wants_tool:
        result = execute(response.tool_call)
        messages.append(result)
    else:
        done = True
```

Best for: research across multiple sources, multi-step debugging, complex data analysis where the path depends on what Claude discovers along the way.

See [Agent Architecture](/agents/agent-architecture) for the full pattern with code.

### When to Escalate

| Move from | Move to | When |
| --- | --- | --- |
| Single prompt | Scripted workflow | You need programmatic validation between steps, context window is too small, you need tool calls between steps, or a single prompt violates too many constraints |
| Scripted workflow | Agent loop | You genuinely can't predetermine the steps — the task requires exploration or the tool-calling pattern is open-ended |

:::tip
Everything at Level 1 and Level 2 has predictable execution — you know the steps, cost, and latency upfront. Agent loops are fundamentally different: non-deterministic, potentially unbounded, and harder to debug. Cross that line deliberately.
:::

## How Does Claude Get Knowledge?

How you give Claude information depends on how much you have and how often it changes. This decision is independent of your complexity level above.

| Strategy | How it works | Use when | Tradeoff |
| --- | --- | --- | --- |
| **Direct context** | Paste content into the prompt | Content fits in the context window and queries are infrequent | Simplest. No infrastructure. Cost scales with input size. |
| **Direct context + [prompt caching](/production/cost-optimization)** | Cache a large static prefix, pay full cost only once | Same content is queried repeatedly | ~90% input cost reduction on cached tokens. Best for static corpora under ~200K tokens. |
| **[RAG](/retrieval/rag)** | Chunk, embed, retrieve relevant pieces | Documents exceed the context window, or you have many documents | Better cost/latency at scale. Requires embedding pipeline and vector store. |
| **Tool-based retrieval** | Give Claude a search [tool](/the-api/tool-use) and let it query on demand | Data is live, dynamic, or requires structured queries (SQL, APIs) | Most flexible. Claude decides what to search for. May increase latency. |

**Decision shortcut:**
- **< 50 pages** of static content — try direct context first. Add [prompt caching](/production/cost-optimization) if you're querying repeatedly.
- **50+ pages** or growing corpus — [RAG](/retrieval/rag). Preprocess once, retrieve per query.
- **Live data** (databases, APIs, dashboards) — tool-based retrieval. RAG adds indexing lag.

You can combine strategies. A common production pattern: RAG for your documentation corpus + a tool for live database queries.

## How Does Claude Connect to Services?

When Claude needs to call external services, you choose how to define and package the tools.

| Approach | How it works | Use when |
| --- | --- | --- |
| **[Direct tool definitions](/the-api/tool-use)** | Define tools inline in your API call with JSON schemas | Tools are specific to your app, few in number, tightly coupled to your logic |
| **[MCP](/mcp/mcp)** | Connect to MCP servers that expose tools via a standard protocol | Tools are reusable across projects, shared with a team, or available as pre-built servers |

**Decision shortcut:**
- Building **one app** with **a handful of custom tools** — define them directly. Fewer moving parts.
- Tools should be **reusable** or **shared across projects** — MCP.
- **15+ tools** — consider MCP to avoid prompt bloat and improve tool selection accuracy.
- Need **both** — start with direct tools, extract to MCP when you find yourself duplicating definitions.

## Common Combinations

Real applications mix patterns. Here's how common use cases map:

| Use case | Complexity | Knowledge | Integration |
| --- | --- | --- | --- |
| Customer support bot | Route by ticket type, chain per handler | RAG over help docs | Direct tools for ticket system |
| Code review assistant | Single prompt (small diffs) or chain (large PRs) | Direct context + tool retrieval for related files | Direct tools for CI/linting |
| Research agent | Agent loop | Tool-based retrieval | MCP for web search + databases |
| Document Q&A | Single prompt | RAG (or direct context + caching for small corpora) | None |
| Content moderation | Single prompt with few-shot examples | Direct context | None |
| Data pipeline | Chain | Tool-based retrieval | Direct tools for database + APIs |
