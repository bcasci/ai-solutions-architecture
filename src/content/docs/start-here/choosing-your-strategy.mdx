You've picked your platform ([API, Claude Code, or Agent SDK](/start-here/choose-your-path)). Now pick the right pattern. Most over-engineering happens here — teams reach for agents when a chain would do, or build RAG when the document fits in a single prompt.

This page covers three decisions:
1. **How complex should my system be?** (complexity ladder)
2. **How do I give Claude the right knowledge?** (knowledge strategy)
3. **How do I connect Claude to external services?** (integration strategy)

## Complexity Ladder

Start simple. Move up a step only when the simpler approach isn't enough. These patterns compose — a router can dispatch to chains, and a chain step can parallelize internally. Pick the simplest combination that meets your quality bar.

**1. Single Prompt**
**Use when:** the task is self-contained, the context fits in the window, and one Claude call can handle it.
One API call, one response. This covers more than you think — summarization, classification, extraction, short code generation, Q&A over small documents. Try this first.

**2. [Chain](/agents/orchestration)**
**Use when:** the output of step N depends on step N-1 being complete.
Sequential Claude calls, each with a focused prompt. Draft → revise → format. Generate → validate → fix. Each step is simpler and more reliable than asking one prompt to do everything.

**3. [Route](/agents/orchestration)**
**Use when:** different input types need different handling.
A classifier sends each input to a specialized pipeline. Support tickets: billing → billing handler, technical → technical handler. Each handler gets its own prompt, tools, and context. Simpler than it sounds — it's just a classifier plus a dispatch table.

**4. [Parallelize](/agents/orchestration)**
**Use when:** subtasks are independent and don't need each other's output.
Run multiple Claude calls concurrently, then aggregate results. Process 50 customer reviews for sentiment, themes, and action items simultaneously. Faster wall-clock time than chaining, but higher total API cost and requires concurrency management.

**5. Evaluator-Optimizer**
**Use when:** output quality varies and you need iterative refinement.
One Claude call generates, another evaluates, loop until a quality threshold is met. Code generation with test validation, content with quality scoring, SQL with execution verification. The iteration count isn't predetermined — that's what distinguishes this from a simple chain.

**6. [Agent Loop](/agents/agent-architecture)**
**Use when:** you can't predetermine the steps and Claude needs tools to interact with the world.
Give Claude tools and a goal. It decides what to do, observes results, and iterates. Research across multiple sources, multi-step debugging, complex data analysis. Higher flexibility, lower predictability.

:::tip
Everything from Single Prompt through Evaluator-Optimizer has predictable execution — you know the steps, cost, and latency upfront. Agent loops are fundamentally different: non-deterministic, potentially unbounded, and harder to debug. Cross that line deliberately.
:::

## Knowledge Strategy

How you give Claude information depends on how much you have and how often it changes.

| Strategy | How it works | Use when | Tradeoff |
| --- | --- | --- | --- |
| **Direct context** | Paste content into the prompt | Content fits in the context window and queries are infrequent | Simplest. No infrastructure. Cost scales with input size per query. Quality may degrade for very long contexts. |
| **Direct context + [prompt caching](/production/cost-optimization)** | Cache a large static prefix, pay full cost only once | Same content is queried repeatedly | ~90% input cost reduction on cached tokens. Best of both worlds for static corpora under ~200K tokens. |
| **[RAG](/retrieval/rag)** | Chunk, embed, retrieve relevant pieces | Documents exceed the context window, or you have many documents | Better cost/latency at scale. Requires embedding pipeline, vector store, and chunking strategy tuning. |
| **Tool-based retrieval** | Give Claude a search [tool](/the-api/tool-use) and let it query on demand | Data is live, dynamic, or requires structured queries (SQL, APIs) | Most flexible. Claude decides what to search for. May make multiple sequential tool calls, increasing latency. |

**Decision shortcut:**
- **< 50 pages** of static content → try direct context first. Add [prompt caching](/production/cost-optimization) if you're querying the same content repeatedly.
- **50+ pages** or growing corpus → [RAG](/retrieval/rag). Preprocess once, retrieve per query.
- **Live data** (databases, APIs, dashboards) → tool-based retrieval. RAG adds indexing lag that makes it a poor fit for fast-changing data.

You can combine strategies. A common production pattern: RAG for your documentation corpus + a tool for live database queries.

## Integration Strategy

When Claude needs to call external services, you have two paths.

| Approach | How it works | Use when | Tradeoff |
| --- | --- | --- | --- |
| **[Direct tool definitions](/the-api/tool-use)** | Define tools inline in your API call with JSON schemas | Tools are specific to your app, few in number, tightly coupled to your logic | Zero overhead. You build and maintain everything. Gets unwieldy past ~15 tools. |
| **[MCP](/mcp/mcp)** | Connect to MCP servers that expose tools via a standard protocol | Tools are reusable across projects, shared with a team, or available as pre-built servers | Ecosystem of pre-built servers. Adds IPC latency and a server process to manage. |

**Decision shortcut:**
- Building **one app** with **a handful of custom tools** → define them directly. Fewer moving parts.
- Tools should be **reusable**, **shared across projects**, or you want the **pre-built MCP ecosystem** → MCP.
- **15+ tools** → consider MCP to avoid prompt bloat and improve tool selection accuracy.
- Need **both** → start with direct tools, extract to MCP servers when you find yourself duplicating tool definitions across projects.

## Combining Strategies

Real applications mix patterns. Here's how common use cases map:

| Use case | Complexity | Knowledge | Integration |
| --- | --- | --- | --- |
| Customer support bot | Route by ticket type → chain per type | RAG over help docs | Direct tools for ticket system |
| Code review assistant | Single prompt (small diffs) or chain (large PRs) | Direct context + tool retrieval for related files | Direct tools for CI/linting |
| Research agent | Agent loop | Tool-based retrieval | MCP for web search + databases |
| Document Q&A | Single prompt | RAG (or direct context + caching for small corpora) | None |
| Content moderation | Single prompt with few-shot examples | Direct context | None |
| Data pipeline | Chain | Tool-based retrieval (read from source) | Direct tools for database + APIs |
